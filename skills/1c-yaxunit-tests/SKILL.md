# /yaxunit-tests — юнит-тесты 1С на YAxUnit

YAxUnit — фреймворк юнит-тестирования для 1С:Предприятие 8.3, поставляется как расширение конфигурации. Тесты пишутся в **отдельном расширении-наследнике**, заимствующем тестируемые объекты основной конфигурации. Запускается через EDT MCP — `mcp__edt-mcp__run_yaxunit_tests`.

## Когда применять

- Покрываешь чистые функции (без БД) — формулы расчёта, маппинг, валидация.
- Покрываешь публичный API общих модулей (CRUD по регистрам, агрегации).
- Готовишь регрессионную защиту перед рефакторингом.
- Не подходит для: тестов UI, длительных интеграций с внешними системами.

## Структура

Три EDT-проекта обычно живут параллельно:

| Проект | Назначение |
|---|---|
| `Конфа` | Основная конфигурация — то, что тестируем |
| `Конфа.YAXUNIT` | Само расширение YAxUnit (фреймворк, скачивается из репозитория [YAxUnit](https://github.com/bia-technologies/yaxunit)) |
| `Конфа.ЮнитТесты` | Тестовое расширение основной конфигурации с тестовыми модулями |

Тестовое расширение и YAxUnit подключаются к тестовой ИБ как два расширения. В продакшен-ИБ — отключаются.

## Создание тестового модуля

### Шаг 1 — `.mdo` тестового общего модуля

Серверный модуль с расширенным доступом — копирует конвенцию реальных модулей конфигурации:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<mdclass:CommonModule xmlns:mdclass="http://g5.1c.ru/v8/dt/metadata/mdclass" uuid="<UUID-V4>">
  <name>ютТесты_МойМодуль</name>
  <synonym>
    <key>ru</key>
    <value>Тесты_Мой модуль</value>
  </synonym>
  <server>true</server>
  <externalConnection>true</externalConnection>
  <clientOrdinaryApplication>true</clientOrdinaryApplication>
</mdclass:CommonModule>
```

UUID **обязательно** генерировать через `python -c "import uuid; print(uuid.uuid4())"` (правило проекта).

Префикс имени (`ют` в примере) определяется в `Configuration.mdo` расширения (`<namePrefix>ют</namePrefix>`).

### Шаг 2 — регистрация в `Configuration.mdo` расширения

```xml
<commonModules>CommonModule.ютТесты_МойМодуль</commonModules>
```

Без этой строки модуль **не подхватится** YAxUnit — даже если `.mdo` лежит на диске.

### Шаг 3 — шаблон `Module.bsl`

```bsl
////////////////////////////////////////////////////////////////////////////////
// Юнит-тесты модуля ОбщийМодуль.МойМодуль.
//
// Общие модули фреймворка YAxUnit (ЮТТесты, ЮТУтверждения) лежат в соседнем
// расширении и невидимы статанализу EDT. Чтобы избежать ложных
// undefined-variable, обращение к ним идёт через ОбщегоНазначения.ОбщийМодуль().
// Имена локальных переменных не должны совпадать с именами общих модулей,
// иначе платформа выдаст 'Поле объекта недоступно для записи'.
////////////////////////////////////////////////////////////////////////////////

//@skip-check bsl-legacy-check-string-literal

#Область ПрограммныйИнтерфейс

Процедура ИсполняемыеСценарии() Экспорт

	МодульЮТТесты = ОбщегоНазначения.ОбщийМодуль("ЮТТесты");

	МодульЮТТесты.ДобавитьТестовыйНабор("Имя набора")
		.ВТранзакции()  // опционально - откатывает данные после каждого теста
		.ДобавитьСерверныйТест("ПроверитьЧтоТо")
		.ДобавитьСерверныйТест("ПроверитьДругое");

КонецПроцедуры

#КонецОбласти

#Область СлужебныйПрограммныйИнтерфейс

Процедура ПроверитьЧтоТо() Экспорт

	МодульЮТУтверждения = ОбщегоНазначения.ОбщийМодуль("ЮТУтверждения");

	// Подготовка тестовых данных
	Результат = МойМодуль.МояФункция(42);

	// Проверка
	МодульЮТУтверждения.Что(Результат, "Описание").Равно(84);

КонецПроцедуры

#КонецОбласти
```

**Ключевые моменты:**

1. `//@skip-check bsl-legacy-check-string-literal` в шапке файла — подавляет диагностику передачи строковых литералов в `ОбщегоНазначения.ОбщийМодуль()`.
2. `МодульЮТТесты`/`МодульЮТУтверждения` — локальные переменные, **не** одноимённые с общими модулями. Иначе runtime-ошибка `Поле объекта недоступно для записи`.
3. `ОбщегоНазначения.ОбщийМодуль("ЮТТесты")` — то же, что прямой вызов `ЮТТесты`, но через БСП-обёртку. Возвращает CommonModule reference, методы вызываются обычным образом.
4. Локальная переменная объявляется в **каждой** процедуре, где используется ассерт. Это разово, не накладно.

## Канонические паттерны

### Транзакция с откатом

```bsl
МодульЮТТесты.ДобавитьТестовыйНабор("ИмяНабора")
	.ВТранзакции()  // ← все тесты набора оборачиваются в транзакцию
	.ДобавитьСерверныйТест(...)
```

Каждый тест выполняется в своей транзакции, которая **всегда откатывается** в конце — даже при `passed`. Безопасно для тестов, пишущих в регистры/документы.

**Транзакция применяется только если `.ВТранзакции()` явно вызван** — иначе изменения остаются в ИБ. Применять:

- ✅ Тест пишет в регистры/документы/справочники/константы.
- ❌ Чистая функция без обращения к БД — накладные расходы транзакции лишние.
- ⚠️ Тест запускает фоновое задание или внешний HTTP-вызов — транзакция не покрывает внешние эффекты, нужно чистить вручную.

### Проверка исключений

YAxUnit **не имеет** надёжного fluent-API для проверки исключений в свободной форме. Используй классический `Попытка/Исключение`:

```bsl
ИсключениеБылоВыброшено = Ложь;
ТекстОшибки = "";

Попытка
	МойМодуль.МетодКоторыйДолженУпасть(НеВалидныйПараметр);
Исключение
	ИсключениеБылоВыброшено = Истина;
	ТекстОшибки = ОписаниеОшибки();
КонецПопытки;

МодульЮТУтверждения.Что(ИсключениеБылоВыброшено, "Должно упасть").ЭтоИстина();
МодульЮТУтверждения.Что(ТекстОшибки, "Текст ошибки").Содержит("Неподдерживаемая");
```

### Фабрика тестовых данных

Если структура данных однотипная — выноси в служебную функцию модуля:

```bsl
#Область СлужебныеПроцедурыИФункции

Функция НовыеПараметры()
	Параметры = Новый Структура;
	Параметры.Вставить("Поле1", 0);
	Параметры.Вставить("Поле2", Ложь);
	...
	Возврат Параметры;
КонецФункции

#КонецОбласти
```

И в тесте переопределяй только нужные поля:

```bsl
Параметры = НовыеПараметры();
Параметры.Поле1 = 100;
```

### Пустые ссылки для тестов

Регистры сведений с измерением `ДокументСсылка.X` обычно принимают `Документы.X.ПустаяСсылка()` — это позволяет писать тесты без подготовки реального документа:

```bsl
Заказ = Документы.ЗаказКлиента.ПустаяСсылка();
МойМодуль.Зарегистрировать(Данные, Заказ);
```

## Запуск через EDT MCP

### Простой запуск всех тестов расширения

```
mcp__edt-mcp__run_yaxunit_tests(
    launchConfigurationName: "<имя launch-конфигурации основной ИБ>",
    extensions: "<ИмяТестовогоРасширения>"
)
```

Без `modules` подхватываются модули, перечисленные в `yaxunit.json` (конфиг YAxUnit). Если такого конфига нет — может вернуться 0 тестов.

### Явный список модулей или тестов

```
mcp__edt-mcp__run_yaxunit_tests(
    launchConfigurationName: "<имя>",
    modules: "ютТесты_М1,ютТесты_М2",
    extensions: "<ИмяТестовогоРасширения>"
)
```

Или ещё точнее — конкретные тесты:

```
mcp__edt-mcp__run_yaxunit_tests(
    launchConfigurationName: "<имя>",
    tests: "ютТесты_М1.ПроверитьА,ютТесты_М1.ПроверитьБ"
)
```

### Перед запуском

После любых изменений `.bsl` или `.mdo` тестового расширения **обязательно** обновить ИБ:

```
mcp__edt-mcp__update_database(
    launchConfigurationName: "<имя>",
    fullUpdate: true,
    autoRestructure: true
)
```

Без этого инфобаза будет работать со старым байт-кодом расширения, а тесты — выдавать ошибки по уже исправленному коду.

**Признак того, что EDT не видит правок:** если правил `.bsl` через инструмент Edit/Write (мимо редактора EDT), а `update_database` вернул `stateBefore: "UPDATED"` сразу после правки — изменения не подхватились. Должно быть `INCREMENTAL_UPDATE_REQUIRED`. См. ловушку #11.

### Если EDT validator показывает ложные ошибки даже после fix

```
mcp__edt-mcp__clean_project(projectName: "<ИмяТестовогоРасширения>")
```

`clean_project` сбрасывает кеш индекса EDT и запускает полную ревалидацию. После него `get_project_errors` обычно показывает реальную картину.

### Отладка одного теста

```
mcp__edt-mcp__set_breakpoint(...)
mcp__edt-mcp__debug_yaxunit_tests(launchConfigurationName, tests: "Модуль.Метод")
mcp__edt-mcp__wait_for_break()
mcp__edt-mcp__get_variables(...)
```

## Ловушки

### 1. Кешированный отчёт MCP

`run_yaxunit_tests` отдаёт отчёт по хешу параметров запуска. Если те же параметры — может вернуться **старый отчёт** даже после обновления кода. Если видишь стектрейс с устаревшими номерами строк или именами переменных — измени параметр запуска (например, добавь `tests: "..."` с явным списком). Хеш изменится, отчёт будет свежий.

### 2. Имя локальной переменной = имя общего модуля = крах в runtime

```bsl
// ❌ ПЛОХО - 'Поле объекта недоступно для записи (ЮТТесты)'
ЮТТесты = ОбщегоНазначения.ОбщийМодуль("ЮТТесты");
ЮТТесты.ДобавитьТестовыйНабор(...);

// ✅ ХОРОШО
МодульЮТТесты = ОбщегоНазначения.ОбщийМодуль("ЮТТесты");
МодульЮТТесты.ДобавитьТестовыйНабор(...);
```

Платформа интерпретирует присваивание имени глобального общего модуля как «запись в свойство» и падает. Имя должно отличаться — конвенция БСП: префикс `Модуль*` (`МодульСозданиеНаОсновании`, `МодульПодключаемыеКоманды` и т.д.).

### 3. РС с уникальным измерением и «дубль через API»

Регистр сведений с уникальным измерением **физически** не может содержать дубликат. Если пытаешься написать тест на «как функция реагирует на дубль» — функция не может его создать через регистр с уникальностью. Такой тест нужно либо удалять, либо тестировать **идемпотентность** (повторная запись не порождает второй record и не падает).

### 4. EDT не видит API соседнего расширения

`undefined-variable` для `ЮТТесты`, `ЮТУтверждения` — false positive статанализатора EDT, который не загружает другие расширения в свой индекс. Лечится исключительно паттерном с `ОбщегоНазначения.ОбщийМодуль(...)` (см. выше). Прямые вызовы `ЮТТесты.ДобавитьТестовыйНабор(...)` **работают в runtime**, но засоряют отчёт валидации.

### 5. Имя расширения для фильтра

В `extensions` параметре MCP передавай имя **из синонима/корневого `name` Configuration.mdo расширения**, а не из имени EDT-проекта. Часто это разные строки: проект `Конфа.ЮнитТесты`, имя расширения `КонфаЮнитТесты`.

### 6. `.ВТранзакции()` — общая транзакция на весь набор

`.ВТранзакции()` оборачивает **весь набор** в одну транзакцию, **не каждый тест в свою**. Если один тест в setup-фазе бросил необработанное исключение — все последующие тесты набора падают с «В данной транзакции уже происходили ошибки!». Setup-фаза должна быть надёжной: предпочитай простые программные создания объектов через `СоздатьДокумент()`/`СоздатьЭлемент()` сложным цепочкам публичных API.

### 7. РС с уникальным ключом `Период + измерения` — миллисекундные конфликты

Если функция пишет в регистр сведений с ключом `Период + X` через `НаборЗаписей.Записать(Ложь)` (без замещения), и ты в тесте вызываешь её **дважды подряд** в одной миллисекунде — получишь «Запись с такими ключевыми полями существует». Платформа использует точность до миллисекунды, и `ТекущаяДатаСеанса()` в одном тесте часто возвращает то же значение.

Решения:
- Не вызывать функцию подряд в setup и потом в тесте.
- В setup использовать прямой `СоздатьДокумент()` минуя публичный API, который пишет статусы.
- Если нужен явный временной зазор — взвесь, не проще ли удалить такой тест: он принципиально time-of-day-зависимый.

### 8. Master-измерения и зависание тестового клиента

Регистр сведений с измерением, помеченным `<master>true</master>`, ссылается на «ведущую таблицу». В проектах с интеграцией внешних источников (например, таблица в MySQL) ведущая таблица часто **физически живёт во внешнем источнике**. Платформа при **любом обращении к регистру** (запись и чтение) делает проверку master-таблицы — и если внешний источник недоступен (а в тестовой среде его обычно нет), сеанс **зависает намертво** без ошибки.

Симптом: тест даёт timeout, после чего весь тестовый клиент перестаёт отвечать на любые вызовы (`run_yaxunit_tests`, `update_database`). Восстанавливается только перезапуском клиента вручную (MCP не умеет его убить).

**Важно**: бьёт не только `СоздатьМенеджерЗаписи() + Записать()`, но и обычные **запросы на чтение** (`ВЫБРАТЬ ... ИЗ РегистрСведений.X ГДЕ ...`). То есть тестировать любую функцию, которая читает или пишет такой регистр, в режиме без MySQL **невозможно** — только через структурное изменение регистра.

Что делать:
- Если регистр сам — **тестируемый объект**: убрать `<master>true</master>` (если бизнес-логика это позволяет), либо поднимать MySQL рядом с тестовой ИБ. Иначе тесты не работают.
- Если регистр **косвенная зависимость** (например, тестируется функция, которая итерирует по списку регистров и одна из них — с master): исключить тест из автоматического прогона, оставив комментарий-обоснование. Покрывать такие сценарии ручным регрессом.
- Перед тестированием регистра-зеркала всегда проверяй `.mdo` на `<master>true</master>` у измерений.

### 9. `ОбработкаПроверкиЗаполнения` не срабатывает при серверной записи

Платформа вызывает `ОбработкаПроверкиЗаполнения` **только при записи через форму** (или явном вызове `Объект.ПроверитьЗаполнение()`). При программной `Объект.Записать(РежимЗаписиДокумента.Проведение)` из серверного кода (тесты, фоновое задание, API) этот обработчик **не вызывается**, и `Отказ = Истина` внутри него ни на что не повлияет.

Симптом: тест `ПроверитьПроведение_Х_БезПоля_Отказ` ожидает исключение при записи документа без обязательного поля, но запись проходит — тест падает с «должно упасть».

Решение — дублирующая проверка в `ПередЗаписью` или `ОбработкаПроведения`:

```bsl
Процедура ПередЗаписью(Отказ, РежимЗаписи, РежимПроведения)
    Если ТипОперации = Перечисления.ТипыОпераций.Простой
        И Не ЗначениеЗаполнено(ПричинаПростоя) Тогда
        ОбщегоНазначения.СообщитьПользователю(
            НСтр("ru = 'Заполните причину'"), ЭтотОбъект, "ПричинаПростоя",, Отказ);
        Возврат;
    КонецЕсли;
КонецПроцедуры
```

`ОбработкаПроверкиЗаполнения` остаётся для UX в форме, `ПередЗаписью` — для серверного контракта.

### 10. Тестируемая функция «молча возвращает» при ошибке

Бывают функции с паттерном:

```bsl
Попытка
    КритическаяОперация();
Исключение
    ЗаписьЖурналаРегистрации(...);
    Возврат;  // тихо выходим, не пробрасывая ошибку
КонецПопытки;
```

Тест, который проверяет «после вызова состояние Х», в этом случае ничего не покажет: функция «прошла», но не сделала. Если такой тест неожиданно зеленеет с пустым результатом — проверь, нет ли подавленного исключения внутри. Часто это потенциальный баг, который стоит зафиксировать отдельным issue.

### 11. EDT держит старый снапшот .bsl при правках через Edit/Write

Если правишь `.bsl` файл в EDT-проекте расширения **не через редактор EDT** (через Edit/Write, внешний редактор, git checkout, sed) — EDT не подхватывает изменения в свой workspace-кеш автоматически. Симптомы:

- `mcp__edt-mcp__update_database` возвращает `stateBefore: "UPDATED"` (а не `"INCREMENTAL_UPDATE_REQUIRED"`) сразу после правки.
- Тесты гоняются на **старом скомпилированном коде**: `run_yaxunit_tests` падает с сообщениями, ссылающимися на устаревшие значения переменных, при том что `Read`/`Grep` файла показывают свежий код.
- Стек-трейс ошибки указывает на корректные номера строк (платформа умеет показывать актуальные позиции в исходнике), но **значения и логика** — из старой версии. Это сбивает с толку: код выглядит правильно, а ошибка как будто из ниоткуда.

**Решение**:

```
mcp__edt-mcp__clean_project(projectName: "<ИмяРасширения>")
mcp__edt-mcp__update_database(launchConfigurationName: "<имя>", fullUpdate: true)
mcp__edt-mcp__run_yaxunit_tests(...)
```

`clean_project` заставляет EDT перечитать файлы с диска и заново их провалидировать. Следующий `update_database` увидит `stateBefore: "INCREMENTAL_UPDATE_REQUIRED"` и реально применит изменения.

Можно потерять часы на ложную диагностику, если не знать про этот кеш — повторные `update_database fullUpdate` без `clean_project` ситуацию не лечат.
