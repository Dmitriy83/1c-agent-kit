# /edt-validate-subsystem — валидация EDT-проекта по подсистеме

EDT-проекты с подключённой БСП обычно содержат 10–14 тысяч ошибок-предупреждений валидатора. Подавляющее большинство — в коде БСП и стандартных подсистем (`СтандартныеПодсистемы.*`, `ОбменДаннымиXDTOСервер`, `УниверсальныйОбменДаннымиXML` и т.д.). Это шум, который маскирует реальные проблемы в проектных объектах.

Скил даёт способ отфильтровать ошибки до объектов, входящих в конкретные подсистемы (обычно — корневую подсистему проекта и её дочерние).

## Когда применять

- Нужно увидеть «свои» ошибки в проекте, без шума БСП.
- Проводишь review качества проекта или готовишь к релизу.
- Хочешь убедиться, что новые объекты (после рефакторинга) не добавили проблем.
- EDT показывает много ошибок и непонятно, какие реально требуют внимания.

## Алгоритм

### Шаг 1 — собрать список FQN объектов из всех `.mdo` файлов подсистем

```bash
grep -h "<content>" \
    "<путь>/<Проект>/src/Subsystems/<Корневая>/<Корневая>.mdo" \
    "<путь>/<Проект>/src/Subsystems/<Корневая>/Subsystems/"*/*.mdo \
    | sed 's/^[[:space:]]*<content>//' \
    | sed 's|</content>||' \
    | sort -u
```

Получишь список FQN вида `Document.ЗаказКлиента`, `CommonModule.ОбменДанными`, `Catalog.Номенклатура`, `Enum.СтатусыЗаказов` и т.п.

### Шаг 2 — передать список фильтром в `get_project_errors`

```
mcp__edt-mcp__get_project_errors(
    projectName: "<Проект>",
    objects: [<массив FQN из шага 1>],
    severity: "ERRORS" | "BLOCKER" | "CRITICAL" | "MAJOR" | "MINOR" | "TRIVIAL",  // по желанию
    limit: 100  // по умолчанию
)
```

Параметр `objects` — массив строк. Поддерживает русские названия типов (`Справочник.X`, `Документ.Y`, `ОбщийМодуль.Z`) и английские (`Catalog.X`, `Document.Y`, `CommonModule.Z`). Фильтр работает по точному совпадению FQN, поэтому передавай ровно то, что вернул шаг 1.

### Шаг 3 — группировать ошибки по типу проверки

В выводе обращай внимание на колонку `Check code` — это идентификатор проверки EDT. Сгруппируй похожие. Часто встречающиеся в проектах на БСП (на которые стоит реагировать):

| Check code | Что значит | Приоритет |
|---|---|---|
| `dcs-ql-hub` | Синтаксическая ошибка в СКД-запросе — отчёт может физически не работать | Высокий |
| `form-legacy-check-event-handler` | На событие формы привязан несуществующий метод — сломанная привязка | Высокий |
| `form-list-ref-use-always-flag-disabled` | У реквизита Ссылка динамического списка нет «Использовать всегда» — стандарт ИТС | Высокий |
| `form-items-single-event-handler` | Один обработчик привязан к одному событию несколько раз | Высокий |
| `md-object-attribute-comment-incorrect-type` | Реквизит Комментарий не соответствует стандарту (длина, multiLine) | Средний |
| `query-in-loop` | Запрос внутри цикла (производительность); часто исправляется одним запросом с `В (&Массив)` или suppression `// @skip-check query-in-loop` |  Средний |
| `ql-join-to-sub-query` | Соединение с подзапросом — переписать через ВТ | Средний |
| `ql-temp-table-index` | ВТ без `ИНДЕКСИРОВАТЬ ПО` — добавить индексы по полям соединения | Низкий (но часто можно сделать массово) |
| `mdo-ru-name-unallowed-letter` | Буква «ё» в имени/синониме/комментарии — стандарт ИТС | Низкий (стиль) |
| `module-structure-form-event-regions` | Обработчик не в стандартной области модуля формы | Низкий (стиль) |
| `bsl-legacy-check-static-feature-access` | Статанализатор не понимает обращение к свойству; **часто false positive** для XDTO/WSПрокси API | Игнорировать |
| `form-legacy-emf-check` («Unsupported button type») | Форма создана внешним редактором, EDT её не парсит, но платформа работает | Игнорировать |
| `export-procedure-missing-comment` | Нет doc-комментария к экспортной процедуре | Низкий (стиль) |
| `empty-except-statement` | Пустой блок `Исключение` | Низкий (стиль) |

### Шаг 4 — после фиксов ревалидировать и проверить

```
mcp__edt-mcp__revalidate_objects(projectName: "<название>", objects: [<FQN исправленных>])
mcp__edt-mcp__get_project_errors(projectName: "<название>", objects: [<те же>])
```

Если кеш диагностики показывает старые результаты после правки `.dcs` или `.form` файлов — выполни `mcp__edt-mcp__clean_project` (он перезапустит полную ревалидацию проекта; занимает 30–60 сек, MCP вернёт timeout, но процесс продолжается).

## Подавление false positives

Для случаев, когда диагностика — false positive (например `query-in-loop` для запроса по 3 разным таблицам, а не по данным):

```bsl
// @skip-check query-in-loop - <короткое обоснование>
Выборка = Запрос.Выполнить().Выбрать();
```

Аннотация ставится **строкой выше** проблемного выражения. Поддерживается EDT BSL-валидатором.

## Типичные паттерны массовых правок

### Паттерн 1: Сломанные привязки `ПриСозданииНаСервере` в формах с пустым модулем

Обычно появляется на формах списка/элемента справочников, созданных через визард. Удалить блок из `.form`:

```python
HANDLER_PATTERN = re.compile(
    r'  <handlers>\s*\n'
    r'    <event>OnCreateAtServer</event>\s*\n'
    r'    <name>ПриСозданииНаСервере</name>\s*\n'
    r'  </handlers>\s*\n'
)
new_content = HANDLER_PATTERN.sub('', content)
```

### Паттерн 2: «Использовать всегда» для реквизита Ссылка динамического списка

Добавить в `<attributes>` блока динамического списка между `</edit>` и `<main>true</main>`:

```xml
<notDefaultUseAlwaysAttributes xsi:type="form:DataPath">
  <segments>Список.Ref</segments>
</notDefaultUseAlwaysAttributes>
```

Имя атрибута (`Список` в примере) узнавай по `<name>...</name>` внутри `<attributes>`.

### Паттерн 3: Реквизит «Комментарий» по стандарту

В `.mdo` документа/справочника заменить:

```xml
<stringQualifiers><length>500</length></stringQualifiers>
</type>
```

на:

```xml
<stringQualifiers/>
</type>
<multiLine>true</multiLine>
```

(`<stringQualifiers/>` пустое = неограниченная длина; `<multiLine>` — после `</type>`, до `<minValue>`.)

### Паттерн 4: Обмен `ё` → `е` массово в `.mdo`

```python
content.replace('ё', 'е').replace('Ё', 'Е')
```

Безопасно для имён/синонимов/комментариев. **Не применять** к BSL-коду — там бывают идентификаторы вида `РазмещёнНаЛинии`.

## Что обычно остаётся после очистки

Рассчитывай, что после прохода по всем приоритетным проверкам в подсистеме останется:

- Несколько `module-structure-*` диагностик с не очевидной причиной (часто кеш EDT показывает их даже после правки)
- `form-legacy-emf-check` для форм со старыми типами кнопок (не фиксится без переделки формы)
- `bsl-legacy-check-static-feature-access` для XDTO/WSПрокси API (false positive)
- Косметика стандарта ИТС (`export-procedure-missing-comment`, `empty-except-statement`)

Решение «добивать или оставить» — за разработчиком; для production-релиза достаточно нулевого `ERRORS` и `BLOCKER` на проектных объектах.
